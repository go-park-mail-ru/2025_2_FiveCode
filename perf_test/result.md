# Нагрузочное тестирование Notes API

## Описание

Данный документ содержит результаты нагрузочного тестирования API сервиса заметок.

**Тестируемые эндпоинты:**
- `POST /api/notes` — создание заметки
- `GET /api/notes/{id}` — получение заметки по ID

**Основная сущность:** Note (заметка) — представляет основную бизнес-ценность приложения для заметок типа Notion.

## Исходная схема БД

Исходный DDL сохранён в файле [init.sql](./init.sql).

**Основные таблицы:**
- `note` — заметки (основная сущность)
- `block` — блоки контента заметки
- `favorite` — избранные заметки пользователей

**Особенности схемы:**
- Materialized View `note_search_index` для полнотекстового поиска
- Триггеры для автоматического обновления поискового индекса
- GIN индексы для триграммного поиска

       n.is_archived, n.is_shared, n.share_uuid, n.created_at, n.updated_at, n.deleted_at,

## Выявленные узкие места

### 1. Ограничение количества соединений PostgreSQL

**Проблема:** При попытке запустить тест с 100 параллельными соединениями (`-c100`) получили ошибку:
```
FATAL: sorry, too many clients already
```

**Причина:** PostgreSQL по умолчанию имеет `max_connections = 100`, а каждый запрос на создание заметки открывает транзакцию.

**Решение:** Уменьшили количество соединений до 20.

**Возможные оптимизации:**
- Увеличить `max_connections` в PostgreSQL
- Использовать connection pooler (PgBouncer)
- Оптимизировать пул соединений в приложении

### 2. Триггеры на обновление поискового индекса

**Проблема:** При каждом INSERT в таблицы `note`, `block`, `block_text` срабатывают триггеры `refresh_search_index`, которые отправляют уведомление через `pg_notify`.

**Влияние:** Дополнительный overhead при массовой вставке данных.

**Возможные оптимизации:**
- Отключать триггеры при массовой загрузке данных
- Использовать отложенное обновление materialized view

### 3. Транзакция на создание заметки

**Проблема:** Создание одной заметки включает 3 INSERT в транзакции:
1. INSERT в `note`
2. INSERT в `block`
3. INSERT в `block_text`

**Влияние:** Увеличенное время на каждый запрос.

### 4. Микросервисная архитектура

**Проблема:** Запрос проходит через несколько слоёв:
- HTTP запрос → Gateway Service
- gRPC вызов → Notes Service
- SQL запрос → PostgreSQL

**Влияние:** При том что SQL выполняется за 0.1 ms, общий latency API составляет 33-44 ms. Основное время уходит на сетевые вызовы и сериализацию.

## Выводы

1. **SQL-запросы оптимизированы хорошо** — используются индексы, время выполнения запроса чтения составляет 0.093 ms.

2. **Основные узкие места находятся не в БД**, а в:
    - Ограничении количества соединений
    - Накладных расходах микросервисной архитектуры (gRPC, HTTP)
    - Транзакционной логике создания заметки

3. **Производительность чтения выше записи** — RPS чтения (160) в 3 раза выше RPS записи (50-59), что ожидаемо для операций INSERT vs SELECT.

4. **Система стабильна под нагрузкой** — при 20 параллельных соединениях ошибок нет, только таймауты.

## Рекомендации по оптимизации

### Краткосрочные (без изменения архитектуры):

1. **Увеличить `max_connections`** в PostgreSQL или добавить PgBouncer
2. **Отключать триггеры** при массовых операциях
3. **Настроить connection pool** в приложении

### Долгосрочные:

1. **Batch INSERT** — группировать создание заметок
2. **Асинхронное обновление** materialized view
3. **Кэширование** часто читаемых заметок (Redis)
